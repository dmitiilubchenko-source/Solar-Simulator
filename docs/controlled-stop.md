# Управляемая остановка и восстановление опыта

Изменения312–315, 18–19 октября2026. Реализованы сохранение последнего завершённого
пакета и исправление потери родителя при первоначальном открытии GUI.
Формулы, интеграторы, размеры пакетов, `dt` и допуски не менялись.

## GUI

«Стоп и копия» прекращает постановку новых пакетов, дожидается текущего
и сохраняет полный checkpoint или bundle с непосредственным родителем.
Окно остаётся открытым; путь появляется в строке состояния.
Обычная «Пауза» сохраняет прежнее поведение и сама не записывает файл.

Пользовательское закрытие окна также запрашивает остановку и копию.
Окно закрывается только после завершения пакета и успешного сохранения.
При ошибке рабочего потока сохраняется предыдущее завершённое состояние,
а не частичный результат неуспешного solver-вызова. Ошибка записи оставляет
окно и данные в памяти, показывает сообщение и допускает повторную попытку.
При сбое worker запись выполняется до показа модального уведомления об ошибке:
отсутствие пользователя не задерживает создание копии. При успешной копии
и уже запрошенном закрытии окно закрывается; отказ записи требует повторной попытки.
Повторные запросы закрытия во время одного пакета не создают новые задания.

Копии находятся в `%LOCALAPPDATA%/SolarSimulator/recovery/solar-*/checkpoint.json`;
при отсутствии LOCALAPPDATA — в `~/.local/share/SolarSimulator/recovery/`.
Каждая запись использует новую папку с UTC-временем и UUID. Старые копии
не перезаписываются. «Recovery-копии…» показывает локальные checkpoint-файлы
(новые сверху, время имени UTC), включая повреждённые. Список не разбирает
полные опыты; проверка происходит при открытии. Повреждённая копия оставляет
прежний опыт и окно выбора. После открытия сохраняются child и parent;
расчёт можно продолжить. Открытие заменяет текущий опыт: сохраните его заранее.
Копии рядом с CLI output открываются обычной кнопкой «Открыть JSON»;
список не ищет пользовательские файлы по всему диску.
Держите нужные опыты отдельно; автоматического удаления recovery-копий нет.

Если расчёт одного пакета занимает долгое время, остановка тоже ждёт его.
Принудительного завершения работающего потока или ослабления допусков нет.
Это сохраняет прежнее разбиение DOP853, от которого зависят численные результаты.

## CLI

`run-until` при KeyboardInterrupt (обычно Ctrl+C) во время расчёта или финальной записи
сохраняет последний целиком полученный пакет в новой подпапке `solar-interrupted-*`
рядом с запрошенным выходным файлом и возвращает код130. Если ни один пакет
не завершён, сохраняется начальный опыт. При обычной ошибке расчёта создаётся
`solar-failed-*`, после чего исходная ошибка передаётся штатной обработке.
В stderr выводятся `recovery_path`, статус и `last_committed_time_seconds`.
Автоматические каталоги `solar-interrupted-*`/`solar-failed-*` исключены
из Git правилами проекта, если output находится внутри checkout. Recovery-копии
с пользовательскими начальными условиями не должны попадать в публикацию.

Запрошенный output не заменяется recovery-копией; input также сохраняется.
Отказ финальной записи также сохраняет готовый результат, даже если цель уже достигнута.
Если recovery рядом с output недоступна, CLI пробует локальный каталог GUI:
`%LOCALAPPDATA%/SolarSimulator/recovery`. JSON-диагностика сообщает fallback,
исходный отказ, цель и факт её достижения. При отказе обеих записей CLI
явно перечисляет ошибки recovery и завершается неуспешно без сообщения
об успешном сохранении. Recovery не гарантирует успех при отказе всех дисков.
Некорректный запрос, отвергнутый до цикла, не создаёт recovery-копии.
Другие команды и экспериментальный continuous CLI сохраняют прежние контракты.

Для продолжения выберите найденный checkpoint/bundle как input нового `run-until`
и задайте конечное время в секундах от начала этого опыта. Настройки, спин,
работа заданной ориентации, события и непосредственный родитель сохраняются
через существующий атомарный writer. Цель GUI/очередь заданий и внутренние
буферы интегратора в checkpoint не входят.

## Проверки и границы

В первоначальных 8 случаях до реализации:7FAIL/1PASS. Набор расширен до12 новых
случаев за счёт остановки до первого пакета, ошибки записи CLI и автоматической
копии после ошибки worker без запроса закрытия. Первый вариант:5PASS/3FAIL.
Два отказа были ошибкой теста, сравнивавшего Windows-путь с JSON без декодирования;
третий выявил реальную потерю parent в конструкторе GUI: полученный snapshot
сбрасывался вызовом `_set_experiment` без аргумента. Старый исходник независимо
воспроизвёл потерю; текущий конструктор передаёт родителя явно.
Прежние тесты проверяли аргумент launcher и загрузку ветки в уже созданном окне;
новый сценарий проверяет непосредственно создание окна с веткой и сохранение.

Дополнительный probe выявил запись только после подтверждения сообщения workererror.
Порядок исправлен, тест требует существование корректной копии уже при открытии
уведомления. Первый полный аудит был намеренно остановлен до завершения;
его журнал сохранён отдельно, он не объявлен успешной проверкой.

Проверяются уникальность и атомарная ошибка записи, сохранность parent/input/output,
отказ worker, повторная попытка записи, закрытие с pending Future, остановка без
следующего пакета и CLI до/после завершённого пакета. GUI выполняется в свежем Tcl;
контролируемые Futures/KeyboardInterrupt не являются измерением задержки реального
Ctrl+C на любой платформе. GUI-тесты используют отдельный LOCALAPPDATA в tempdir.

Изменение312:18 установленных версий совпали с constraints, Windowsx64/CPython3.14t
проверены, `pip check` прошёл. [Основной путь установки](reproducibility.md)
теперь отражён также в README и user-guide. Новая чистая среда не создавалась.

Сохранение запускается на управляемой остановке/закрытии/обработанном отказе,
а не периодически после каждого пакета. Потеря питания, жёсткое убийство процесса,
повторное прерывание самой записи и нехватка места не дают гарантии сохранения.
Существующие копии не удаляются. Это не новая квалификация годовой точности.

## Смена опыта342

Новый сценарий, сброс, открытие JSON, готовые лунный/солнечный профили и
открытие recovery сначала проверяют новый опыт, затем сохраняют прежний
полный результат вместе с parent в новую solar-replaced-* копию. При
ошибке записи окно/опыт/графики остаются прежними; отмена диалога ничего
не сохраняет и не заменяет. Инициализация окна не создаёт копию. Ветка
редактора и возврат к parent сохраняют свой прежний явный путь записи.
Копия создаётся перед каждым таким переходом, даже при t=0: это сознательная
защита конфигурации без хрупкого признака dirty. Копии автоматически не удаляются.
