Изменение 311, 18 октября 2026. Два варианта используют одни и те же 10 тел,
начальные данные и EIH 1PN + фиксированные Sun/Earth J2. Вращение Луны
и приливы в них не добавляются. SI, SSB, Ecliptic J2000, JD 2461321.5 TDB.

## Запуск из исходников

В GUI перед кнопкой «Солнечная система: EIH + J2» появился выбор
`standard/strict`; предварительно выбран `strict`. Выбор в списке сам
не меняет открытый опыт: профиль создаётся нажатием кнопки. Открытие JSON
сохраняет его настройки. Ручное изменение настроек убирает неподходящую
профильную подпись; сама подпись показывает совпадение старта и настроек,
а не сертификат текущей траектории.

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m solar_simulator solar-sandbox strict.json --profile strict --backend rust
.\.venv\Scripts\python.exe -X utf8 -B -m solar_simulator run-until strict.json year.json --time 31557600 --batch 20
```

CLI без `--profile` сохраняет прежний Standard. Для него можно явно указать
`--profile standard`. Прежний `application_profiles.solar_sandbox()` также
не изменён. Новый выбор реализован в `solar_profiles.py`; он меняет только
допуск Strict и проверяет область профиля, не дублируя физические формулы.
В выводе создания CLI есть `solar_profile`: старт, область и ограничения.
Формат checkpoint не менялся; повторное открытие определяет профиль по данным.

Историческая область относится к конкретным сеткам эпох, году и пакетам20.
Другой batch, редактирование системы, срок за пределами года и результаты
между выходными эпохами требуют своей проверки. `current_trajectory_certified`
остаётся false: распознавание настроек не является новым научным измерением.
Portable155 этого переключателя не содержит. В новой сборке наличие явного
выбора отражено в BUILD-INFO.json (`explicit-standard-strict-selection`);
актуальную проверенную сборку указывает dist/LATEST.txt в исходном проекте.

## Полный аудит с обязательным native

```powershell
.\.venv\Scripts\python.exe -X utf8 -B scripts/build_native.py
.\.venv\Scripts\python.exe -X utf8 -B scripts/check_project.py --require-native
```

Этот режим перед pytest требует настоящий скомпилированный PyO3-модуль,
проверяет API и независимый случай свободного движения одного тела.
Установленный Maturin-пакет с Python-обёрткой допустим: проверяется внутренний
модуль расширения и тождественность экспортируемых функций.
Тот же preflight повторяется в процессе pytest. Любой пропуск теста или
модуля при сборе даёт неуспешный итог и список пропусков. Это намеренно
строгий полный аудит, включая причины пропуска, не связанные с Rust.
Неполный API требует явной пересборки, автоматической подмены Python нет.

Без `--require-native` сохраняется обычная политика pytest. Это не обещание,
что весь набор тестов пройдёт без установленного Rust: отдельные имеющиеся
проверки уже требуют его. Само приложение сохраняет поддержанные Python-режимы.
Preflight не доказывает совпадение бинарного файла со всеми исходниками;
для воспроизводимого native-аудита сначала выполняется команда сборки выше.

## Проверка изменения

До реализации 15 новых случаев отказали. Первая реализация дала 7 PASS/8 FAIL:
сравнение `Vector3` оказалось сравнением объектов, а реальный Maturin-пакет
ошибочно отвергался по внешнему `__init__.py`. Причины исправлены без изменения
физического ядра. Следующие 30 относящихся тестов прошли за 24,47 с.
Добавлены проверки точного продолжения Strict по прежнему checkpoint в обоих
backend. Итог полного прогона приведён ниже.

Новый годовой расчёт, загрузка JPL, новая portable и измерение ускорения
в этот этап не входят. Старые результаты и исходный неуспех Standard сохранены.

Полный итог: **2011 Python-тестов, 19 Rust-тестов, оба cargo fmt** прошли.
Режим `--require-native`, пропусков нет. Время общего прогона
326.10 с. Исходники, публичные JSON/данные и native-бинарник
не менялись во время прогона; SHA до/после совпали. Это проверка интерфейса,
совместимости и существующего набора моделей, не новая годовая квалификация.
