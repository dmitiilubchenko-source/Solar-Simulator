# Понятная диагностика сохранённого опыта

Новый режим включается явно:

```powershell
.venv/Scripts/python.exe -X utf8 -B -m solar_simulator inspect experiment.json --reliability
```

Команда читает checkpoint или branch, возвращает прежний JSON отчёта и добавляет
один раздел `numerical_reliability` со своим `schema: 1`. Без флага JSON прежний.
Файл и родитель branch не изменяются. Орбита не интегрируется, допуски и
контрольная точка не переписываются. Обычный Python API `cli.report(experiment)`
сохранён; явный расширенный API — `solar_simulator.inspection.report(experiment)`.

## Что означает отчёт

| Раздел | Что можно узнать | Чего он не доказывает |
|---|---|---|
| `model` | Newton/EIH1PN, fixed J2, prescribed Q2, dynamic Q2 или контакты; ограничения модели | Полноту физики реальных небесных тел |
| `execution` | Какой путь использует обычный `advance` при этих настройках; доступен ли требуемый native API | Каким процессом/бинарником были получены прошлые состояния |
| `adaptive_controls` | rtol, position/velocity atol, error_control, relative_pair; для dynamic rotation — её дополнительные допуски | Глобальный предел ошибки. Для Verlet поле `null`: эти допуски там не используются |
| `time_and_packets` | Текущее время и назначение settings.dt | Число шагов прошлого пакета, расписание выдачи или внутренние адаптивные шаги: checkpoint их не хранит |
| `invariants` | Уже доступные E/P/L и энергетический баланс в SI, с указанием применимости | Ошибку координат или скорости из одного малого дрейфа энергии |
| `qualification` | Совпадает ли start/settings с factory Standard/Strict текущей установки; области ранее проверенных сценариев | Исторические SHA, среду, границы пакетов и аттестацию данной траектории |
| `accuracy` | Честное отсутствие оценки, если нет независимого сравнения | Численную точность произвольного пользовательского опыта |

`global_position_error_metres`, `global_velocity_error_m_per_s` и
`jpl_residual_metres` в этом режиме всегда `null`: текущая точка сама по себе
не содержит эталона. `current_trajectory_certified` остаётся `false`, даже
при совпадении factory-профиля или наличии исправного native.

**Три разных вопроса:** численная ошибка измеряется относительно независимого
решения той же задачи; дрейф инвариантов проверяет её баланс; JPL residual
сравнивает согласованные данные, эпохи, оси, шкалы времени и физические модели.
Одно не заменяет другое. Сведения об исходной эпохе/данных остаются в обычных
`origin`/`epoch_jd_tdb` полях отчёта; для модельной задачи без origin эпоха не угадывается.

## Интегратор, native и пакеты

DOP853 работает в SciPy. Backend Rust использует Rust point forces, а не
исследовательский Rust adaptive solver. Для связанного вращения выбирается
RotationDOP853 с собственными блоками ошибок. Контактные режимы используют
Verlet. Точное сопоставление — в [архитектуре376](runtime-reliability-376.md).

`native.status=available` означает проверку compiled loader, нужного API и
fingerprint библиотеки для текущих настроек; это не научная квалификация.
При отсутствующем/stale native отчёт состояния всё равно доступен, но
`native.status=unavailable`. Никакого переключения орбитального расчёта в Python
не происходит. Python backend не требует native и не проверяет его наличие.

В Verlet dt — номинальный физический шаг (`configured_physical_step_seconds`);
конечный шаг до заданного времени может быть короче. Последний фактический
внутренний шаг не хранится и показан как `internal_step_seconds: null`.
В DOP853 dt*steps задаёт интервал пакета,
внутренние шаги выбирает solver. Частота выдачи/просмотра и пакетизация — разные
величины; их прошлое расписание нельзя восстановить из одного checkpoint.
Поэтому соответствующие неизвестные поля равны `null`, а не выдуманному dt.
Если имеется запись траектории с recipe, используйте существующую команду:

```powershell
.venv/Scripts/python.exe -X utf8 -B -m solar_simulator check-recipe TRAJECTORY_DIRECTORY
```

Strict recipe проверяет точную среду/код; добавление отчётного кода может сделать
старый recipe несовместимым для строгого replay при той же версии приложения.
Это не миграция checkpoint и не повод подменять его SHA. Чтение состояния и
просмотр ранее сохранённой траектории имеют отдельный контракт.

## Какие балансы применимы

- Newton points: механическая энергия, полный P и L с сохранённым passive spin.
  Stored spin не означает интегрирования ориентации или rigid-spin энергии.
- EIH: согласованные Noether-величины до 1PN, с остатками отброшенного порядка;
  ньютоновский COM остаётся описательным. Это не Newton energy certificate.
- Fixed J2: включён потенциал фигур; орбитальный L может обмениваться моментом
  с заданными осями. Для EIH+figures дополнительно отсутствуют смешанные figure/c² члены.
- Prescribed Q2: учитывается сохранённая работа ориентации. Команда не восстанавливает
  её интеграл из двух состояний и не обещает постоянство механической энергии.
- Dynamic Q2: полная orbital+rigid-spin энергия и суммарный орбитальный+spin L;
  орбитальный L отдельно не сохраняется. Это не режим EIH или контактов.
- Контакты/слияния: нужен бюджет `E + dissipated + model_offset - orientation_work - initial_E`.
  Механическая энергия может физически изменяться. Значения берутся из существующей
  диагностики и сохранённых ledger-полей, без новых физических формул.

Смысл и ограничения формул сохранены в [физике](physics.md),
[EIH](relativity.md), [динамическом вращении](nbody-rotation.md)
и [контроле ошибок](error-control.md).

## На какие измерения можно ссылаться

[375](current-runtime-375-validation.md) проверял конкретные10 тел DE441,
год, EIH+fixed Sun/Earth J2, Strict/per-body/relative Earth–Moon,
125 эпох и9 holdout, конкретные numerical/native/environment bindings.
[376](runtime-reliability-376.md) проверял четыре фиксированных Newton IC,
включая high-e и две фазы e=.99, на49 заданных эпохах. Его high-e результаты
не дают универсальной гарантии для любой орбиты с таким же эксцентриситетом.
Изменение массы, скорости, модели, recipe или среды не наследует эти числа автоматически.

Исторический source-bound replay376 теперь включается отдельно:

```powershell
.venv/Scripts/python.exe -X utf8 -B -m scripts.assess_runtime_reliability376 verify --historical
```

Он проверяет сохранённые массивы и точные старые source bytes, не интегрирует
новые орбиты и возвращает `current_runtime_qualified: false`. Без флага проверка
актуальных исходников остаётся строгой и отклоняет несовпадающие SHA. Старые
протоколы/численные результаты не изменены; snapshot inspection-before377
сохранён в `scripts/validation/inspection-before377.zip` с фиксированным SHA.

[Уточнение main/tag/GitHub Release](release-status-20261028.md) отдельно объясняет
устаревшую надпись0.3.1 в README main. Этот отчёт не публикует новый выпуск.
