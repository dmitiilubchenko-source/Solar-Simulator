# Контролируемый опыт с округлением

15 октября2026,159, до результатов.
Все исходные данные, epochgrid, Decimal100reference, допуски и критерии
из [протокола156](kepler-phase-protocol.md) сохраняются.
Только e=.95,2периода,60эпох. Ни силы, ни runtime, ни defaults не меняются.

Offlinepatch функции rk_step заменяет только суммирование стадий:
1. math.sumprod вместо dot для взвешенных сумм стадий;
2. перенос остатка округления принятого обновления состояния на следующий
   шаг; стадии получают y+carry, carry меняется только при принятом шаге;
3. оба изменения вместе.
Все три варианта сравниваются при uncapped/dynamicd32/dynamicd64.
Контроль без правок должен побитно совпасть с156/158. Одинаковые snapshots,
rtol/atol и RHS; контроллер может выбрать иной путь из-за округления.
Результаты, стоимость и неуспехи каждого варианта сохраняются. Один
удачный вариант не выбирается по факту для продвижения в production.
Если улучшение есть, необходимы отдельные заранее заданные отложенные
сценарии и проверка lifecycle/rejectedstep до возможного внедрения.

Первичные источники: [SciPy rk_step](https://raw.githubusercontent.com/scipy/scipy/v1.18.1/scipy/integrate/_ivp/rk.py),
[Python math.sumprod](https://docs.python.org/3/library/math.html#math.sumprod).
SciPy-коэффициенты и accepted/rejected алгоритм сохраняются; подстановка
в отдельном процессе исследования не распространяется на приложение.
Python longdouble в данной Windows-среде имеет52бита мантиссы и
не используется как якобы независимая расширенная точность.
