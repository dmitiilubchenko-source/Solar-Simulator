# Solar-Simulator — облегчённый процесс научной проверки

**Проектное предложение (версия 0.3, 20 октября 2026 г.)**\
**Статус: согласовано как проектное предложение; внедрение требует отдельного задания и согласования.**

## 1. Зачем это нужно

После исчерпания лимита Consensus обеспечить продолжение научной работы над Solar-Simulator без привязки к одному сервису поиска. Повысить прослеживаемость формул, допущений и результатов проверок **с минимальными затратами на поддержку**.

Новый «научный движок», сеть сервисов и второй контур валидации **не требуются**. Приоритет — использовать то, что уже есть, а не строить альтернативную инфраструктуру. Само наличие публикации или успешного теста не доказывает физическую достоверность реализации.

## 2. На что уже можно опереться

Перед работой Codex должен проверить **актуальное локальное рабочее дерево**, включая ветку, незакоммиченные изменения и действующие инструкции. Публичный репозиторий может отставать от локального.

В публичном Solar-Simulator (проверено по состоянию на 20.10.2026) уже представлены:

- `docs/project-map.md` — карта компонентов и порядок ведения реестра файлов;
- `docs/offline-data.md`, `scripts/prefetch_physics_sources.py` — локальные первичные данные и проверки их целостности;
- `scripts/de441_reader.py`, `scripts/export_jpl_bundle.py` — работа с эфемеридами и воспроизводимыми сравнениями;
- `scripts/assess_*.py`, `scripts/independent_*.py`, `scripts/verify_*.py` — проверочные и исследовательские скрипты;
- `docs/*-protocol.md`, `docs/*-validation.md`, `docs/*-validation.json` — ранее зафиксированные критерии, результаты и ограничения;
- `scripts/check_project.py`, `scripts/project_inventory.py` — общепроектные проверки и реестр структуры.

Список носит справочный характер: проверять существование, назначение и действующий контракт файлов в рабочем дереве. **Не создавать заново** аналоги имеющихся инструментов. Старые неуспешные отчёты, контрольные суммы и исходные данные не переписывать и не удалять.

## 3. Минимальный рабочий процесс для новой научной задачи

1. **Проверить существующие материалы.** Найти относящиеся к задаче протоколы, отчёты, первичные публикации и закреплённые данные. Определить, чего действительно не хватает.
2. **Найти первоисточник при необходимости.** Использовать доступный поиск: статьи издателей, arXiv, NASA ADS, OpenAlex, Crossref и др. Никакой обязательной разработки API-клиентов. Для уже сохранённого и проверенного текста не делать сетевой запрос без причины. Недоступность внешнего API не блокирует работу, если локальных проверенных первичных материалов достаточно для конкретного вывода.
3. **Проверить конкретное утверждение.** Для взятой из источника формулы указать документ, страницу/раздел/номер уравнения (если они есть), обозначения, допущения, систему координат, единицы и временную шкалу там, где это существенно. Метаданные агрегатора или аннотация не заменяют первичный текст. Если уравнение не найдено либо доступен лишь пересказ — сказать об этом явно.
4. **Связать утверждение с реализацией.** Указать существующий модуль, профиль и проверки. Для новых физических изменений заранее определить допустимые критерии; не выбирать пороги по результатам теста.
5. **Применить существующие проверки.** По задаче использовать аналитические/численные тесты, независимые реализации и подходящие эталонные данные. Не требовать JPL для искусственной задачи, к которой астрономические эфемериды неприменимы.
6. **Оставить краткий отчёт.** Что подтверждено, что именно запускалось, с какими входными данными и какими результатами, а что осталось неизвестным. Отчёт не должен объявлять невыполненные проверки пройденными. Для воспроизводимого численного прогона обязательны полный SHA коммита, состояние рабочего дерева, версии значимых зависимостей, параметры запуска и SHA-256 конкретных входных файлов или ссылка на проверенный manifest с их хешами. При незакоммиченных изменениях сохранить воспроизводимый снимок изменений (например, diff с SHA-256 и хешами неотслеживаемых используемых файлов); один SHA коммита не описывает такой прогон. Если ключевые исходные байты или изменения не зафиксированы, воспроизводимость отметить как `INCOMPLETE`, не изменяя задним числом статус самого численного теста.

Поиск литературы и её разбор остаются **вне runtime**. Никаких автоматических изменений физики по одному найденному совпадению.

## 4. Одна небольшая карточка вместо нескольких схем

На первом этапе достаточно **одной Markdown-карточки на конкретную научную задачу** в существующей документации проекта. Дополнительная JSON Schema, база доказательств, отдельный оркестратор и новая CLI-команда пока не нужны.

### Шаблон карточки

```markdown
# Проверка: <название задачи / модели>

**Статус:** <см. правила ниже>
**Граница задачи:** <что проверяется и что не проверяется>

## Источник и формула
- Первоисточник: <авторы, работа, DOI/официальный URL>
- Проверенное место: <страница, раздел, номер уравнения;
  если их нет — точно описать доступный фрагмент>
- Формула / утверждение: <кратко, своими обозначениями>
- Допущения: <область применимости, аппроксимации>
- Соглашения: <единицы, система отсчёта, шкала времени, оси>
- Доступ к полному тексту: <проверен / недоступен>

## Связь с проектом
- Код / сценарий: <пути, профиль>
- Действующий протокол и результаты: <ссылки на канонические docs/...; не копировать их содержимое>
- Независимость: <что действительно независимо,
  а что повторно использует одну статью, модель или данные>

## Проверка и вывод
- Критерий: <зафиксирован до запуска / ранее утверждённый>
- Фактически запущено: <точные команды, параметры, версии существенных зависимостей>
- Воспроизводимость численного прогона: <полный Git commit SHA; git status;
  при незакоммиченных изменениях — сохранённый diff/snapshot и SHA-256>
- Входные данные для численного прогона: <пути и SHA-256
  либо ссылка на проверенный manifest; если файлов нет — причина>
- Результат: <значения, отклонения, статус каждого применимого критерия>
- Ограничения / невыполненные действия: <явно>
- Итог: <что подтверждено и чего утверждать нельзя>
```

Карточка **не обязана появляться при каждой правке кода**: она нужна там, где вводится или существенно меняется научная модель, формула, набор исходных данных либо научное утверждение. Для уже документированной модели — сначала ссылаться на её действующие материалы, не плодить копии. **Протокол и его результаты — единственный источник действующих критериев, измерений и статуса соответствующего прогона.** Карточка служит указателем на них и кратко фиксирует контекст задачи. Если протокол или результаты обновились, проверить актуальность ссылок и вывода карточки; не поддерживать вторую независимую версию измерений.

## 5. Значение статусов

Статус относится к **конкретной проверке или утверждению**, а не автоматически ко всей модели.

| Статус | Когда применять |
|---|---|
| `PASS` | Применимая проверка реально выполнена и прошла заранее заданный критерий. |
| `FAIL` | Применимая проверка реально выполнена и не прошла критерий; результат сохранить. |
| `INCOMPLETE` | Для обязательного вывода не хватает источника, исходных данных, выполненного теста или иной существенной информации. Причина указывается. |
| `NOT_APPLICABLE` | Проверка не относится к поставленной задаче: например, JPL-сверка искусственной системы двух тел. Причина обязательна. |

Отсутствие выполнения обязательного теста — `INCOMPLETE`, а не `NOT_APPLICABLE`. Неприменимость внешнего эталона не отменяет применимые аналитические, численные и другие проверки. Если модель требует учёта обмена энергией или момента импульса, нельзя подменять её верификацию законом сохранения ньютоновской энергии.

## 6. Источники и независимость

Для поиска можно использовать:

- [NASA ADS](https://ui.adsabs.harvard.edu/) и [arXiv](https://arxiv.org/) — профильные научные публикации;
- [OpenAlex](https://openalex.org/), [Semantic Scholar](https://www.semanticscholar.org/) — поиск и связи между исследованиями;
- [Crossref](https://www.crossref.org/documentation/retrieve-metadata/rest-api/) — DOI и библиографические метаданные;
- [JPL Horizons](https://ssd.jpl.nasa.gov/horizons/) и [NAIF SPICE](https://naif.jpl.nasa.gov/naif/) — подходящие астрономические данные и средства их интерпретации.

Это **варианты по необходимости**, не обязательные подключения. Наличие API не делает источник достоверной проверкой формулы. Не нужно строить отдельные адаптеры, кэш или общий поисковый слой, пока ручной поиск действительно не станет повторяющейся проблемой.

- Одна работа, найденная в OpenAlex, Crossref и ADS, остаётся **одной работой**.
- Препринт и журнальная версия одной работы обычно относятся к одному происхождению доказательства; сверять версии и отличия.
- Horizons и данные DE441 из того же семейства — **не два независимых астрономических эталона**.
- Независимая реализация алгоритма, независимая теория и независимые наблюдения — **разные типы независимости**.
- Когда полный текст отсутствует, не приписывать источнику непроверенный номер формулы и не объявлять его подтверждением математической корректности.

## 7. Поэтапный подход без большого внедрения

**Этап A — сейчас: только согласование предложения.** Сохранить этот документ как необязательную проектную идею; ничего не менять в коде и не подключать API.

**Этап B — по отдельному запросу: один демонстрационный пример.** Выбрать уже существующую научную проверку, найти её первоисточник и протокол и оформить одну карточку по шаблону. Изменения — только в документации, без новых модулей и обязательного полного прогона всех тестов. Сначала убедиться, что такой карточки ещё нет.

**Этап C — по возникшей необходимости:** если карточки реально сокращают неоднозначности и повторяющаяся ручная работа мешает развитию, отдельно рассмотреть *один* небольшой помощник (например, поиск по существующим отчётам). Только после доказанной пользы решать, нужен ли API-адаптер. Новые схемы, автоматический pipeline, несколько сервисных интеграций и централизованный реестр пока **отложены**.

Приливы, новая модель вращения и другие физические расширения **не являются этапом данного предложения**. Их приоритет определяется отдельным планом физики и текущими результатами её валидации.

## 8. Минимальные условия для принятия подхода

1. Не создан второй конкурирующий механизм научной проверки.
2. Для формулы из внешнего источника видны первичный текст, точное место и допущения либо честно указано, чего не удалось установить.
3. Зафиксирована разница между дублирующими источниками и действительно независимыми свидетельствами.
4. Сохраняются старые `FAIL`, история измерений, источники и SHA, а критерии не смягчаются задним числом.
5. `NOT_APPLICABLE` используется только по объяснимой неприменимости, а незавершённые обязательные проверки остаются `INCOMPLETE`.
6. Никаких изменений физических формул, начальных условий, численных решателей, сохранений, интерфейса или пользовательских сценариев только ради этого предложения.
7. Для воспроизводимого численного прогона обязательны SHA коммита, учёт `dirty`-состояния и SHA-256 использованных файлов данных (необязательно повторять хеши в карточке, если они уже проверяемо закреплены в действующем manifest).
8. Карточка ссылается на действующий протокол и отчёт и не становится альтернативным источником критериев или результатов.
