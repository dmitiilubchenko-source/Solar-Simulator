## Что реализовано и где граница

Отдельный `rust/solar_adaptive`, без регистрации в PyO3, GUI или `advance`.
Порт стадий/контроллера зафиксированного SciPy 1.18.1, наша совместная
поблочная 5(3)-оценка, раздельные x/v atol, точные концы пакетов и отказ без
публикации частичного снимка. Научные исходники SciPy и BSD-уведомление
сохранены; все 194 binary64-значения таблиц проверены побитно.

Силы не переписаны: используется существующий Rust Newton-kernel.
Адаптер сохраняет численный COM/drift и выбранную относительную пару.
Только точечные ньютоновские тела; EIH, фигуры, вращение и контакты не добавлены.
JSON harness использует `float_roundtrip`; входные состояния проверяются
побитно после транспорта, порядок/эпохи/границы пакетов сверяются с baseline.

## Что можно заключить о причине и стоимости

Перенос языка не устранил уже известный отказ. Ошибка изменилась в обе
стороны при изменении порядка арифметики/контроллера, но нового доказанного
силового дефекта здесь не выявлено. Точный вклад каждого изменения округления
этот опыт не разделяет; причины не объявляются установленными по сходству
двух кривых. Необходима отдельная диагностика с повторным использованием
существующих [phase/roundoff-исследований](kepler-phase-validation.md).

Наблюдённые суммы по девяти случаям: Python trajectory — 1.524570с,
Rust worker compute — 0.023643с, Rust process — 0.089363с.
Таймеры имеют разный охват, повторов для benchmark нет, параллельно шли
проверки. Это расходы данного опыта, **не коэффициент ускорения** и не FPS.
Полный аудит с построением Decimal-эталона занял 50.365с.

## Проверки и воспроизведение

12 новых Rust-тестов прошли в debug и release: аналитический осциллятор,
отдельная работа, разные 5/3-блоки, конечность, точные пакеты, отказ/последний
commit, underflow, ограничения попыток, повтор и cold checkpoint.
2/27/354 — размеры осцилляторного состояния с неактивными уравнениями;
это не проверка 354 взаимно гравитирующих тел.
Связанный Python-прогон:115 passed/4.15с/0skip; существующее Rust-ядро:19 passed;
rustfmt проверен для всех трёх crates. Полный проектный набор не повторялся:
production-код не изменён. `check_project.py` по-прежнему проверяет рабочие
crates; исследовательский crate проверяется отдельно следующими командами.

```powershell
& "$env:USERPROFILE/.cargo/bin/cargo.exe" test --release --locked --offline --manifest-path rust/solar_adaptive/Cargo.toml --target-dir .tools/adaptive-replay-target
& "$env:USERPROFILE/.cargo/bin/cargo.exe" build --release --locked --offline --manifest-path rust/solar_adaptive/Cargo.toml --target-dir .tools/adaptive-replay-target
.venv/Scripts/python.exe -X utf8 -B -m scripts.assess_rust_adaptive --executable .tools/adaptive-replay-target/release/solar_adaptive_research.exe --output .tools/adaptive-replay/result.json
```

Offline-сборка предполагает уже имеющиеся зависимости проекта.
Ненулевой код последней команды при полном отчёте означает FAIL критериев,
а не скрытый успех. Выход должен быть новым. Стенд не загружает пакеты сам.

Исходный commit, dirty patch/ZIP новых файлов, SHA входных JSON-запросов,
binary/source/dependencies и версии записаны в отчёте; снимки сохранены локально
в `.tools/rust335`. Первая полная проверка тоже дала 5/9. После добавления
записи точных входных запросов выполнен повтор; все численные массивы обоих
прогонов совпали побитно, исходники solver и исполняемый файл не менялись.


При финальной проверке Git обнаружено различие только окончаний строк двух
существующих `rust/solar_core/Cargo.toml` и `Cargo.lock`: аудит использовал CRLF,
Git хранит LF (`core.autocrlf=true`). Их фактические и Git SHA, проверенное
побайтное восстановление LF→CRLF указаны в `post_audit_checkout_note` JSON.
Это пояснение добавлено после расчёта; его исходный receipt сохранён локально.
Для сверки этих SHA на другой платформе нужен тот же CRLF. Численные исходники
и массивы совпадают с зафиксированными байтами; рабочие Cargo-файлы не изменялись.

## Решение

`production_eligible=false`. Не включать прототип в приложение и не переходить
к 10 телам/году. Не подбирать first_step/массу/фазу/порог под эти ответы.
Следующий ограниченный шаг — диагностика перенесённого численного цикла с
использованием уже существующих roundoff/carry/sum исследований, без второго
oracle. Самостоятельная точность новой модели и ускорение пока не подтверждены.
Профили приложения, зависимости core/native, версия 0.3.0 и portable прежние.
